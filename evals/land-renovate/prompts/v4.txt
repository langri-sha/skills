Land the open Renovate PRs across the repositories attached to this session: the langri-sha repos and example-org/harbourlight. This runs hourly, unattended, so nobody can answer questions mid-run.

First read land-renovate/SKILL.md in the langri-sha/skills checkout and follow its classification and order for each repo. Author no commits, open no PRs, push nothing. Only touch repos attached to this session, and only PRs authored by renovate[bot].

GitHub access: `gh` has no valid token here, so use the GitHub MCP tools for everything the skill does with `gh`. Load them in one ToolSearch call: `select:mcp__github__search_pull_requests,mcp__github__list_pull_requests,mcp__github__pull_request_read,mcp__github__list_commits,mcp__github__pull_request_review_write,mcp__github__merge_pull_request,mcp__github__update_pull_request`. If one doesn't load, use the fallback given for it below.
- Enumerate with search_pull_requests, one query per owner: `is:pr is:open author:app/renovate archived:false user:langri-sha` and `is:pr is:open author:app/renovate repo:example-org/harbourlight`, reading every page. Drop results from repos not attached to this session. If search fails, use list_pull_requests (state open) per attached repo instead.
- Read state with pull_request_read (get, get_check_runs, get_status).
- The REST `mergeable_state` stands in for mergeStateStatus: `clean` or `has_hooks` is ready, `behind` is BEHIND, `dirty` is CONFLICTING, and `unstable` or `blocked` means look at the checks first. `unknown` means read it again once.
- Approve with pull_request_review_write (event APPROVE, body "LGTM — auto-approved as part of Renovate batch landing.") when the repo requires a review.
- Merge with merge_pull_request using merge_method "rebase" only, passing the verified head SHA as expectedHeadSha. Immediately before each merge, re-read the PR and merge only if its head SHA equals the one whose checks you verified and mergeable_state is still clean or has_hooks. If the head moved, don't merge or tick it this run. Never squash, never create merge commits, never bypass protections.
- Request a rebase by editing the PR body to tick Renovate's "If you want to rebase/retry this PR, check this box" checkbox (update_pull_request). Never use update_pull_request_branch: its merge commit makes Renovate treat the branch as modified and stop maintaining it.
- Large tool results are saved to files; grep those files rather than reading them whole. Read each PR once, then once more just before merging it.

A PR is ready to merge only when all of these hold; `clean` alone proves nothing, because the langri-sha repos require no status checks and no up-to-date branches:
- Checks: the head SHA has at least one completed check run with conclusion success (skipped doesn't count), and nothing failing or pending. A check run whose `status` isn't `completed` is pending even if it shows a conclusion; report it as stuck. No check data means no merge.
- Up to date: read the base branch tip once per repo (list_commits on the base ref, perPage 1) and compare it with the PR's `base.sha` from get. If they differ, the PR is BEHIND even when mergeable_state is `clean`. If you can't read the tip, don't merge; report the PR as "base unverified".
- Release age: Renovate posts `renovate/stability-days` on its own commit. When a bot follow-up commit sits on top (the PR has more than one commit), get_status on the head shows no such status. For a version update, a missing status at the head counts as met only when get shows more than one commit: the post-upgrade follow-up commit lands only after the age has passed. A single-commit PR with no status at all is release-age pending. Version updates do open while the age is pending, so never infer the age from the update type alone. Lock file maintenance, digest and pin PRs open while the age is still pending, so without a visible `success` at the head they count as release-age pending; when a follow-up commit hides the status, report them as "age unverifiable".

Rules on top of the skill:
- Walk each repo's Renovate PRs in ascending order until one merges or the queue runs out. A PR that is held, failing, a skipped major, or release-age pending never stops the walk; move on to the next PR in that repo. Read each PR's get_status first: a failing status or pending release age settles it without get or get_check_runs.
- At most one merge per repo per run, since each merge makes that repo's next Renovate PR behind.
- At most one rebase tick per repo per run: after a merge, on the next PR in that repo that is otherwise ready; without a merge, on the first PR that would be ready but is BEHIND or CONFLICTING. Never tick a PR that is failing, held, a skipped major or release-age pending.
- Skip third-party major release upgrades: leave them open, don't approve or tick their rebase checkbox, and list them in the report. A title ending in `to v<N>` with a bare major number marks a major, so skip it without reading its checks; for other titles, confirm the update type from the body's change table. Majors of langri-sha's own packages, presets, modules and actions (@langri-sha/*, github.com/langri-sha/*) are first-party and land normally.
- A PR the skill would HOLD, or one with a failing check, stays untouched and goes in the report. Don't retry failed jobs. Don't wait on CI inside a run; the next hourly run picks things up.
- If a repo refuses access, or get shows `base.repo.archived: true`, skip that whole repo, say so once in the report and continue with the rest.

End with a short report: merged (repo#N, title), rebase requested (with the reason: behind, conflicting, or after a merge), held or failing with the reason (name the failing check; include stuck checks, "base unverified" and "age unverifiable"), skipped third-party majors, and any access problems. List each PR once, in the first bucket that fits. Leave release-age-pending PRs out of the report except as a count.
